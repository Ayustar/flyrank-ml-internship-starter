Abstract

Content that ranks in search can decay quietly, and with thousands of pages a team often notices too late which one to fix first. I asked whether a model can rank pages with falling impressions better than a simple hand-written rule when it is tested on clients it has never seen. I used an anonymised 30,000-page starter slice of FlyRank search data, a stale-and-visible baseline rule, and a Random Forest scored with client-grouped cross-validation after a leakage audit. The result is directional decision support for human reviewers, not a forecast and not evidence that any edit causes recovery.

1. Introduction

FlyRank publishes content straight into client websites and then watches search data to optimise it. A recurring problem sits in that cycle: pages that rank well can slowly lose impressions and clicks, and with thousands of pages per client, the question is which page a human editor should look at first.

Today that triage is done with hand-written rules: if a page is stale and visible, flag it. Rules like these run in production and work, but their thresholds are chosen by hand and they struggle when many signals interact. This project is a small case study of that gap. I build one transparent rule as a baseline, then test on the same pages whether a learned ranking does better on clients it has never seen. The output is a ranked review queue with a reason code and an action label for each page. "The right page" means the right page to review first, not a page guaranteed to improve.

2. Data

I used the anonymised starter dataset shipped with the FlyRank ML Internship: pages after filtering to pages with impressions and at least 90 days of age, one row per page. The larger warehouse release was not used for these results. The data contains observable search and engagement signals only. It has no client names, domains, URLs, queries, or product decision flags.

Label (proxy). A page counts as declining when its impressions trend is "down" over the current window. This is a current-window proxy, not a future outcome, and it is used only as the outcome to evaluate against.

3. Methodology

Baseline

Pages not updated for 90 or more days with 500 or more impressions are flagged and ranked by staleness and log impressions. The rule uses no label information.

Model and features

A Random Forest on observable numeric features. The label is built from last-30-day and previous-30-day impressions, so the columns from those two windows () were removed. A first version that kept them scored AUC near 0.95 with a perfect top 50, and a feature-importance check traced that result to those columns.

Validation

Five-fold cross-validation grouped by client, so every page is scored by a model that never saw its client. Baseline and model are compared on the same pages with the same metrics.

Leakage checks

No product flags, no trend columns, no future-window inputs, and no columns from the label's own 30-day windows. Single-column AUC screening and a feature-importance review were both used. A random-split comparison shows how much a looser design flatters the result. The 90-day totals still contain the label windows, which is listed under limitations.

5. Limitations and honest framing

  • The label is a current-window proxy, so the model ranks pages that look like decliners, not pages that will decline.
  • The sample is a 30,000-page starter slice, so results are directional and not a benchmark on the full warehouse.
  • The 90-day totals (impressions, clicks, sessions) cover the same period as the label, so they may still carry some information about it. A feature window that ends before the label window would be stronger.
  • Results come from one validation design. A time-aware test would be stronger.
  • Drops can come from consolidation, seasonality, or search-result changes that the features cannot see.
  • Nothing here shows that a refresh causes recovery.

6. Ranked recommendations

Each page gets one reason code (first match) and an action. Priority combines model risk (60%) and visibility at stake (40%). The queue has pages. The top 10 are shown without identifiers.

Human review

An editor checks every queued page: is the drop real over a longer window, did a related page absorb its demand, is it seasonal, and does the action fit the page?

What should not be automated

  • Publishing or rewriting content straight from the queue
  • Deleting, merging, or redirecting pages
  • Bulk title or meta changes
  • Skipping review because confidence is high
  • Claiming a refresh caused a recovery without a controlled test

Monitoring

Each month, re-score the previous top 50. Re-review if its decline rate falls more than 10 points, the base rate shifts more than 5 points, a new client is added, or reviewers reject over half of a queue.
